# Workflows and business rules

## Evidence and interpretation

The following **46 workflow families** cover the discovered application surfaces. Each family may contain several separately guarded commands. The [operation contracts](evidence-operation-contracts.md) reproduce all 344 exported non-JSX functions, including signatures, complete branches and dependencies. The [private contracts](evidence-private-data-contracts.md) supply internal validators, SQL helpers, numbering, migration and seed logic. [Command mapping](evidence-command-mapping.md) links individual data commands back to UI components and persistence requirements. These companions are necessary for exact inputs, rules and secondary branches; the family descriptions do not replace them.

Source behavior is VERIFIED where cited. Browser navigation and selected editor states are observed; successful business submissions were deliberately not performed against stored records. Unit tests exercise disposable in-memory data. Runtime verification is therefore per test/capture, not blanket end-to-end verification.

## Shared workflow envelope

Start by logging in as a permitted role, open the specified page and select the relevant active record where required. View/search/filter/pagination controls change UI state only. Add/Edit opens the existing editor with source-defined defaults or selected record values. Submit invokes the named command; client-required flags and handler validation run before command validation. For local SQL workflows, the normal successful envelope is `mutate` → command → persist SQLite snapshot → readState → render updated view and run the editor's close/reset/select behavior. Command failure displays the editor error callback or alert and returns false. Cancellation closes/discards the draft only where that component's handler does so; it must not be implemented as a new delete operation. Exact destination/close behavior is in each component handler ledger.

Local SQL operations are synchronous after asynchronous startup. Workbook/file/PDF operations and remote APIs are asynchronous. Native confirms/reason prompts are part of archive/void flows; blank reasons and dismissed prompts do not authorize a command. Archive, cancel, void and physical row deletion are distinct operations.

## State machines and calculations

Main job states: NEW → IN_PROGRESS or CANCELLED; IN_PROGRESS → COMPLETED, HOLD or CANCELLED; HOLD → IN_PROGRESS or CANCELLED; COMPLETED → IN_PROGRESS for rework. CLOSED and CANCELLED are terminal. CLOSED is produced by the payment/handover command, not the manual status selector. Completion requires a current invoice. `src/db.ts:2037-2100,2348-2389` is authoritative; historical comments or old low-level helpers must not override actor-aware entry points.

Checklist stage order is NEW, IN_PROGRESS, COMPLETED, CLOSED, with exact label arrays in `LIFECYCLE_CHECKLIST`. Substatus is derived from the first unchecked item (or final item once complete), not an independent writable status. Rework/cycle history and artifact reconciliation must remain explicit.

Invoice math (`src/invoice-math.ts:23-45`): round each qty×rate to two decimals; sum rounded lines; clamp flat discount between zero and subtotal; distribute discount proportionally, with final line absorbing rounding remainder; compute and round GST per discounted line; sum taxable/GST; round total. Supported GST types/rates are constants in the type/constant appendix. Material billing claims and late-material additions must not double-bill rows.

Payment mode is UPI, Cash, Card, Bank transfer or Other; Other requires detail. Payment is one full invoice total, not an editable arbitrary amount. Current Pending invoice, COMPLETED job, checked Google review reminder, no active previous payment and positive total are prerequisites. The atomic command creates payment/receipt, clears invoice, advances CLOSED, creates gate pass/delivery acknowledgement and completes delivered checklist evidence. Failure rolls back the unit of work. Legacy Partial statuses can still exist in historical data; they do not authorize adding a partial-payment UI.

Booking dates/capacity, material quantity accounting, purchasing lifecycle and input-specific checks are preserved exactly in the command/private-validator appendices. All TypeScript status unions, nullable fields, enum values and source defaults are in [type contracts](evidence-types-and-constants.md). No new state or transition is proposed by this document.
